# Contributing Guide

Contributions through issues or pull requests are welcome. This page covers development-environment setup, the script reference, coding conventions, and common extension workflows. For architectural background, see [Architecture Overview](/guide/advanced/architecture); for request conventions, see [API and Data Layer](/guide/advanced/api-and-data).

## Development Setup

**Requirements**: Node.js ≥ 20.9 and npm; Windows is recommended (directory scanning, launching executables, process timing, and system fonts all rely on the local filesystem).

```bash
git clone https://github.com/Halory-Ito/vnweb.git
cd vnweb
npm install
npm run db:push
npm run dev          # Development mode http://localhost:3000
```

Production mode:

```bash
npm run build
npm run start        # http://localhost:8999, listening on 0.0.0.0
```

On Windows you can also double-click `init.bat`: the script checks the environment, installs dependencies, fills in missing settings from `data/example/`, initializes the database, builds the app, and adds the project directory to the user's `PATH`.

::: warning init.bat rebuilds the database
If a database already exists, the script first backs up `local.db` and its `-wal` / `-shm` / `-journal` sidecar files to `backups/db/`, then creates an empty one. Close any running vnweb service and Drizzle Studio before running it, and keep a separate backup of your own.
:::

::: danger Next.js version
This repository uses **Next.js 16**—its APIs, conventions, and file structure may differ from the usual tutorials. Before writing code, read the relevant guides in `node_modules/next/dist/docs/` and watch for deprecation notices. That notice block is generated by `next dev` and will be recreated if you delete it.
:::

`package.json` is the source of truth:

| Script                | Actual command                                                                 | Purpose                                                      |
| --------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `dev`                 | `next dev`                                                                     | Dev server on port 3000                                      |
| `build`               | `next build`                                                                   | Production build (standalone output)                         |
| `start`               | `next start -p 8999 --hostname 0.0.0.0`                                        | Start the production server                                  |
| `cli`                 | `tsx cmd/tui.ts`                                                               | Run the command-line tool                                    |
| `build:cli`           | `node scripts/build-cli.mjs`                                                   | Build the standalone CLI bundle                              |
| `build:standalone`    | `node scripts/build-standalone.mjs`                                            | Build a standalone package that runs without the source tree |

| `lint` / `lint:fix`   | `oxlint` / `oxlint --fix`                                                      | Linting and auto-fix                                         |
| `lint:output`         | `oxlint --format=unix >> oxlint-report.txt`                                    | Write a lint report                                          |
| `fmt` / `fmt:check`   | `oxfmt` / `oxfmt --check`                                                      | Formatting and format check                                  |
| `tauri`               | `node scripts/run-tauri.mjs`                                                   | Run Tauri                                                    |
| `tauri:dev`           | `node scripts/run-tauri.mjs dev`                                               | Tauri dev mode                                               |
| `tauri:build`         | `node scripts/prepare-tauri-resources.mjs && node scripts/run-tauri.mjs build` | Build the desktop installer                                  |
| `tauri:prepare`       | `node scripts/prepare-tauri-resources.mjs`                                     | Prepare embedded resources                                   |
| `docs:dev`            | `vitepress dev docs`                                                           | Preview the docs locally                                     |
| `docs:build`          | `vitepress build docs`                                                         | Build the docs                                               |
| `docs:preview`        | `vitepress preview docs`                                                       | Preview the built docs                                       |

**Testing convention**: skip Vitest tests. Smaller page styling, animation, or interaction changes are verified by the user; agents only make the code change and run static checks (`tsc`, `oxlint`, `oxfmt`), and don't run browser tests unless explicitly asked.

## Coding Conventions

### Components and Logic

- Keep a single component file under **200 lines**; consider splitting it into subcomponents past 150 lines.
- Extract business logic into custom hooks; components should only render.
- Prefer the existing shadcn/ui components in `components/ui`, and prefer the outlined style.
- Write custom components using Tailwind CSS v4 syntax.
- Don't nest a card inside another card, and don't add `secondary` hint content to components—keep them lean.
- Always mind responsive layout when changing a page, and keep the styling consistent with the existing code.
- Use `--app-font-family` for the global font everywhere; don't differentiate with `font-mono` / `font-sans` / `font-serif` (except in the font preview area, where paths / numbers / code may use `font-mono` per the design guidelines).
- Watch error boundaries and rendering performance: avoid a local change re-rendering the whole page.
- Component borders must respect the "Borderless" toggle in system settings.

### Dependency Management

Before adding a new dependency, check whether an existing one can do the job; prefer native APIs and libraries already in the project. axios, react-query, Jotai, Zod, Drizzle, ExcelJS, hls.js, and other common capabilities are already included.

### API Layer

- Put cross-module domain requests in the root-level `api/` (`@/api`), split by domain and re-exported from `api/index.ts`.
- Put module-local requests in `features/xxx/xxx-api.ts` and export them from the module entry file.
- Put domain types in the root-level `types/` (`@/types`), exported from `types/index.ts`; types used only inside a module can stay in that module.
- Implement all API server logic in `route.ts` files under `app/api`.
- Use the `api` instance wrapped in `lib/request-utils.ts`; don't call `fetch` in components.
- Standardize axios calls on the `api.request({ method, url })` form.

### Directory Structure

```text
features/xxx/
├── hooks/        Interaction and business hooks
├── components/   Subcomponents
├── data/         Static data, examples, prompts
├── views/        Page-level views
├── lib/          Module-local utilities and constants
├── xxx-api.ts    Module-local requests
└── index.ts(x)   Module entry point
```

## Submission Flow

1. Fork the repository and create a branch.
2. Make your changes and test them yourself.
3. Before committing, run:

   ```bash
   npm run lint
   npm run fmt:check
   npm run build
   ```

4. Open a pull request describing the purpose of the change and how you verified it.

`lint-staged` runs `npm run lint` on `*.{js,jsx,ts,tsx,mjs,cjs}` and `oxfmt --no-error-on-unmatched-pattern` on all files.

Project habit: check the matching item in `plan.md` when you finish a feature; when fixing a bug, check `errors.md` first and delete the entry once it's fixed.

## How to Add a Feature Module

1. Create `xxx/` under `features/`, with `hooks`, `components`, `data`, `views`, `lib`, and `index.ts(x)` as specified.
2. If it needs a page, add `page.tsx` / `layout.tsx` at the matching path under `app/` and put page-level views in `views/`.
3. Define cross-module types: create `types/xxx.ts` and add `export *` in `types/index.ts`.
4. Define requests: for cross-module use `api/xxx.ts` and export it in `api/index.ts`; for module-local use `features/xxx/xxx-api.ts`.
5. Put the server implementation in `app/api/xxx/route.ts`, export the HTTP verb functions you need, and return `{ data }` or `{ error }`.
6. If it needs a database table, define it in `db/schema.ts` and run `npm run db:generate` to generate the migration.
7. If it needs documentation, add a page under `docs/guide/feats/` and a nav entry in `docs/.vitepress/guide-modules.ts`; mirror it to the matching path under `/en/` and use absolute paths for internal links.

## How to Add a Platform Provider

1. Create `xxx-provider.ts` under `lib/providers/` implementing the `GameProvider` interface (see [Platform Integrations and WebMCP](/guide/advanced/platform-integrations)).
2. Register it in the `GAME_PROVIDERS` array in `lib/providers/registry.ts`; fill in `capabilities` as needed.
3. Add a config template in `data/example/platform.json` and add read / write and validation logic in `lib/settings/platform-settings.ts`.
4. If it's a character source, also implement `CharacterProvider` and register it in `lib/providers/characters/metadata.ts` and in `getCharacterProviders()` in `registry.ts`.
5. To expose the capability to models, add a WebMCP tool following the flow below.

## How to Add a WebMCP Tool

1. Define the tool-name constant and Zod input schema in `webmcp/xxx/lib/xxx-tool-schema.ts`.
2. Register the tool with `useWebMCP` in `webmcp/xxx/hooks/use-xxx-tool.ts`; make sure `ensureWebMcpRuntime()` has been called before registering.
3. If it needs generative UI cards, implement a confirmation component under `webmcp/xxx/components/`.
4. Export the tool name, schema, hook, and component from `webmcp/xxx/index.ts`.
5. Document it in the built-in tool list on the [AI Assistant and WebMCP](/guide/feats/ai-assistant) page.

## Troubleshooting

| Symptom                                           | What to do                                                                       |
| ------------------------------------------------- | -------------------------------------------------------------------------------- |
| `npm run dev` reports an incompatible Next.js API | Read the matching guide under `node_modules/next/dist/docs/`                     |
| Database table doesn't exist                      | Run `npm run db:push` or `npm run db:migrate`                                    |
| Port already in use                               | Adjust the `-p` flag in the `start` script or close the process holding the port |
| lint / fmt fails                                  | Run `npm run lint:fix` and `npm run fmt` first                                   |
| New page missing from the docs nav                | Check `guide-modules.ts` and the locale settings in `config.mts`                 |
